# AI 驱动数据模拟方案调研报告

> 调研时间：2026-08-05
> 数据库背景：文体业务 ODS 层（jianengliang / training / vmdb，约60张表）
> 目标：在接入真实数据前，生成足够真实的模拟数据，用于标签设计、数据清洗验证

---

## 核心思路

传统模拟数据的做法是：想好每个字段的规则，然后按规则填数据。这需要你对业务非常熟悉，否则生成的数据虽然格式合法，但业务逻辑乱套（比如优惠券发放给了没下过单的人，或者退款金额大于订单金额）。

AI 方法换了一个角度：**不问"这个字段填什么"，而是问"这类用户会做什么事"**。

具体来说：先创造一批虚拟用户（叫 Persona），每个虚拟用户有自己的特征（比如"价格敏感的大学生"或"经常给公司订场地的行政专员"），然后让 AI 代入这个角色，模拟他在你的系统里的行为。这个行为过程自然会产生跨越多张表、逻辑自洽的数据。

---

## 为什么这种方法更适合你

你面临的问题是：**没有业务专家**，不清楚字段之间的关联规则。

Persona 方法绕开了这个问题。LLM 对"一个学生在文体场馆消费"这件事有天然的认知，它知道：学生倾向于用折扣券、会在周末买票、可能多人拼单。这些知识不需要你编码，只要你描述清楚"这是个什么样的用户"。

另外，Persona 方法对你**标签设计**的帮助是直接的——因为 Persona 的特征属性本身就是候选标签。你生成数据的同时，就在做标签原型设计。

---

## 完整流程

### 第一步：建立字典数据（基础，约半天）

在生成任何用户行为数据之前，需要先准备好系统里的"参照物"——场馆、运动类型、票价、优惠券模板、课程这些基础配置数据。

这些数据用 LLM 直接生成即可，不需要 Persona，只需要告诉 LLM "请生成10个真实感的文体场馆名称、地址和容量"。

**本项目需要的字典数据：**

- 场馆（5-10 个，包含名称、地址、运动类型）
- 运动类型（羽毛球、游泳、篮球、舞蹈…）
- 优惠券模板（面值、适用范围、有效期等，约 20 种）
- 培训课程（课程名称、价格、课时）
- 演出项目（剧场演出的基础信息）

这些数据是后续所有行为数据的"舞台"，必须先有。

---

### 第二步：设计 Persona 库（核心，约半天到一天）

Persona 是你对"用户类型"的设定。不需要太多，**10-20 个典型类型**就足以覆盖大部分行为场景。

每个 Persona 包含以下维度：

| 维度 | 说明 | 示例 |
|------|------|------|
| 用户类型 | 这是什么人 | 大学生、白领、家长、企业行政、老年人 |
| 价格敏感度 | 会不会抢折扣、用优惠券 | 高（每单必用券）/ 中 / 低（不在乎价格） |
| 偏好场景 | 喜欢哪类消费 | 订场打球、买游泳票、看演出、报培训课 |
| 活跃时段 | 什么时候用系统 | 工作日晚上 / 周末 / 节假日 |
| 消费频次 | 多久来一次 | 每周 / 每月 / 偶尔 |
| 注册渠道 | 从哪来的 | 小程序 / iOS App / 线下录入 |
| 生命周期 | 注册多久了、现在活跃吗 | 新用户 / 成熟用户 / 流失中 |

**文体业务的典型 Persona 示例：**

```
Persona A：价格敏感的大学生
- 消费：买学生游泳票 + 团购折扣
- 行为：每次都搜优惠券再下单，经常在周末下午
- 产生的数据：j_member + j_member_order(游泳票) + j_coupon(折扣券使用) + 积分记录

Persona B：企业行政采购
- 消费：批量订羽毛球场地 + 购买培训课程套餐 + 使用企业礼包
- 行为：月底集中下单，金额大，基本不用普通折扣券
- 产生的数据：j_member_order + j_order_field(多个时段) + m_trade_order(培训)

Persona C：亲子家庭用户
- 消费：周末带孩子看演出 + 亲子游泳
- 行为：提前购票、使用亲子套票、偶尔退款改期
- 产生的数据：theatre_ticket_sell_detail + j_member_free_ticket + j_member_order_refund

Persona D：沉默流失用户
- 消费：注册后买过1-2次，最近6个月没来
- 行为：曾领了优惠券但没用，账户有积分
- 产生的数据：j_member + j_coupon(未使用) + j_points_records(少量)

Persona E：高频健身爱好者
- 消费：每周来打球，有专项卡，经常充值
- 行为：刷卡入闸、用储值卡消费
- 产生的数据：vmdb_h_member_card + vmdb_h_member_record + vmdb_m_enter_gate
```

> **为什么这对标签设计有帮助**：你现在定义的这些 Persona 属性（价格敏感度、偏好场景、生命周期），就是你之后要打的标签。等数据生成后，可以直接对照 Persona 设计验证标签逻辑是否正确。

---

### 第三步：模拟行为，生成数据（核心执行）

有了 Persona，接下来的做法是：让 LLM **代入角色**，决定"这次会做什么"，然后把这个决策翻译成数据库记录。

**整个过程分两个层次：**

**层次一：让 LLM 做行为决策**

给 LLM 一个 Persona 描述和一个时间背景，问它这个用户今天会做什么。

```
提示词示例：
你现在扮演一个20岁的大学生，经常在周末来场馆买游泳票，价格敏感。
今天是周六下午，你准备来游泳。
场馆信息：[已生成的场馆字典]
可用优惠券：[已生成的优惠券模板]

请描述你的完整操作步骤，并以 JSON 格式输出你的行为决策：
- 选哪个场馆
- 买什么类型的票
- 是否使用优惠券（哪张）
- 最终支付金额
- 支付方式
```

**层次二：把行为决策翻译成数据库记录**

把上一步的 JSON 决策，让 LLM（或规则代码）映射为对应表的 INSERT 数据。一次行为会同时产生多张表的数据：

```
"买了一张游泳票，用了折扣券" → 产生：
  j_member_order（一条订单主记录）
  j_order_ticket（一条游泳票记录）
  j_order_coupon（一条优惠券使用记录）
  j_coupon 状态更新（优惠券变为已使用）
  j_points_records（一条积分记录）
```

**关键**：因为这些数据来自同一个"用户行为"，它们的外键关系天然一致，不需要你手动维护。

---

### 第四步：批量生成

上面的流程每次处理一个用户的一次行为。批量生成的思路是：

1. 从 Persona 库里随机挑选一个 Persona
2. 随机设定一个时间场景（比如某个周末下午）
3. 执行第三步的模拟
4. 把结果追加到数据集里
5. 重复 N 次

重复 100-500 次，就能产出覆盖多种用户类型的数据集。对于数量更大的需求（万级以上），可以在确认 Persona 和逻辑正确后，用 Python 脚本接管批量执行，不必每条都调用 LLM（LLM 只需要负责"写出这类 Persona 的通用数据生成脚本"，脚本本身执行时不需要再调 LLM）。

---

### 第五步：补充脏数据和边缘案例

真实系统里不会全是完美的数据，你的清洗方案需要包含异常情况。在基础数据生成完之后，专门让 LLM 生成一批问题数据：

- 手机号格式错误的用户记录
- 优惠券过期了但仍被标记为"使用中"的记录
- 退款金额超过订单金额的异常记录
- 身份证验证失败但身份证字段填了假号码的记录

做法：在 Prompt 里明确写"请生成包含以下问题的数据：[问题描述]"，LLM 很擅长生成这类边缘案例。

---

### 第六步：验证数据质量

生成完之后跑几个基本检查：

**结构检查（必做，用 SQL 或 Python）：**
- 外键是否都能找到对应主键（订单里的 user_id 在 member 表里是否存在）
- 时间序列是否合理（创建时间不能晚于更新时间）
- 金额计算是否自洽（订单金额 - 优惠金额 ≈ 实付金额）

**语义抽样检查（用 LLM）：**
随机抽 10-20 条记录，让 LLM 以"业务审查员"的角色检查这些记录是否符合常识。LLM 会直接指出不合理的地方（比如"一个17岁学生买了企业级培训套餐"）。

## 生成数量参考

| 阶段 | 数量目标 | 用途 |
|------|---------|------|
| 阶段一（验证方案） | 各核心表 50-200 条 | 验证流程是否走通，标签候选探索 |
| 阶段二（正式开发） | 各核心表 1000-5000 条 | 支撑数据清洗、填充方案开发 |
| 阶段三（压测/扩充） | 万级以上 | 用脚本批量生成，不再调 LLM |

## 关于多表一致性（技术补充）

不管用不用 Agent 框架，有一条规则必须遵守：**先生成被依赖的表，再生成依赖它的表**。

本项目的依赖顺序（简化）：

```
第1批生成（无依赖）：
  场馆信息、运动类型、课程、演出项目、优惠券模板

第2批生成（依赖第1批）：
  用户（j_member / vmdb_h_member / t_student）

第3批生成（依赖第2批）：
  订单（j_member_order / vmdb_m_trade_order / m_trade_order）
  专项卡（vmdb_h_member_card）

第4批生成（依赖第3批）：
  订单明细、订单场地、游泳票、积分记录、消课记录、入闸记录
```

每一批生成时，把前一批已有的 ID 提供给 LLM，告诉它"外键必须从这些 ID 里选"。这样外键关系就能保证合法。

## 一个完整的执行示例（Persona A，大学生买游泳票）

**输入（给 LLM 的提示词）：**

```
你正在扮演以下用户：
- 年龄：21岁，在读大学生
- 价格敏感度：高，每次都会找最便宜的票
- 偏好：游泳，周末活跃
- 已有账号：member_id = 1023

可用场馆（从已生成的字典里）：
  venue_id=3, 名称=xx健身中心, 有游泳池
  venue_id=7, 名称=xx体育馆, 有游泳池

可用优惠券（从已生成的字典里）：
  coupon_code_id=12, 面值8元, 适用游泳票, 有效期至2026-09-01
  coupon_code_id=15, 面值5元, 适用全场, 有效期至2026-08-31

场景：2026年8月3日（周日）下午3点，你准备去游泳。

请以 JSON 格式输出你的购买决策，包含：
venue_id, ticket_type, coupon_used(coupon_code_id or null),
original_price, discount_amount, pay_amount, pay_way
```

**LLM 输出（行为决策）：**

```json
{
  "venue_id": 3,
  "ticket_type": 3,
  "coupon_used": 12,
  "original_price": 28.00,
  "discount_amount": 8.00,
  "pay_amount": 20.00,
  "pay_way": "3",
  "reasoning": "选最近的游泳馆，用面值更大的8元券"
}
```

**翻译为数据库记录（这步可以用代码模板自动化）：**

```sql
-- j_member_order（订单主表）
INSERT INTO j_member_order VALUES (
  9001, 1023, 3, 20.00, 8.00, 20.00, 'ORD20260803001023',
  '2', '3', '3', '2026-08-03 15:12:00', ...
);

-- j_order_ticket（游泳票）
INSERT INTO j_order_ticket VALUES (
  8001, NULL, 'ORD20260803001023', 1023, 'TK2026080300456',
  '成人单次游泳', 3, 3, NULL, '2026-08-03 15:12:00', ...
);

-- j_order_coupon（优惠券使用）
INSERT INTO j_order_coupon VALUES (
  501, 'ORD20260803001023', [coupon_id], '2026-08-03 15:12:00'
);

-- j_points_records（积分增加）
INSERT INTO j_points_records VALUES (
  ..., 1023, '138xxxxxxxx', 200, '2026-08-03 15:12:00', '购买游泳票', ...
);
```

整个过程，外键一致、时间逻辑正确、金额自洽，全部来自同一个"行为决策"。

## 标签设计如何从这套数据中受益

这套数据生成完后，你可以做这些分析来推导标签：

**直接用（从 Persona 定义推导）：**
- 每个 Persona 的属性直接就是标签候选。比如 Persona A 对应的用户，价格敏感度=高、生命周期=成熟活跃用户、偏好场景=游泳，这些就是该用户应有的标签值。

**从数据分布中观察（探索性）：**
- 哪些用户领了优惠券但从未使用？（潜在流失信号标签）
- 哪些用户每次下单都用了满减券？（价格敏感标签依据）
- 哪些用户的消费跨越了票务+培训+场地三个业务域？（高价值复合型用户）

**验证标签逻辑（开发阶段）：**
- 写好标签计算 SQL 后，在这套模拟数据上跑一遍，验证"企业采购用户"标签是否把 Persona B 的用户全部打到、有没有误打其他类型用户。

## 实施建议

**先从最小可行的方案开始：**

1. 手写 5 个 Persona 描述（不需要代码框架，就是文字描述）
2. 用任意 LLM（你的 API）逐一模拟这 5 个 Persona 各做 10 次操作
3. 把输出翻译成 SQL，导入测试库
4. 确认数据合理性、标签方向是否有感觉
5. 满意后，把这个过程写成 Python 脚本批量化

**不推荐一开始就搭 Agent 框架**：Agent 框架（CrewAI、LangGraph）适合流程复杂、需要反复迭代验证的场景。在你对业务和数据都还不熟悉的探索阶段，用简单的 Prompt + Python 脚本更容易调整，更容易看到每一步在做什么。等 Persona 设计和数据模板稳定后，再考虑是否需要自动化框架。

**关于数据量：**
先不要追求量，10-20 个 Persona × 每人 20 条行为记录 = 200-400 条主表数据，足够设计 5-10 个标签并验证其逻辑。量大了反而增加调试难度。
