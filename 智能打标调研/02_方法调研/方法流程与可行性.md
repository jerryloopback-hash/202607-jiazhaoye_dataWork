# 智能打标方法库 · 针对本库的可行性与流程

> 面向「佳兆业文体」用户数据库（ODS 层，三套源系统：一起吗 C 端 / 场馆 B 端 / 培训），
> 汇报前置调研用。说明「在这个库、这个项目上，哪些机器学习/深度学习方法可行、各自流程是什么思路」。
> 方法按"可行性从高到低"排序；数据依赖以表名/字段/注释为第一依据，测试库仅用于链路演示。

## 0. 数据资产速览（据此判断方法可行性）

| 资产类型 | 代表表（前缀已省） | 可用于 |
|---|---|---|
| 用户主实体 | `j_member`(C端)、`h_member`(场馆)、`t_student`(培训) | 打标主体、一人一行宽表 |
| 消费/交易行为 | `j_member_order(_detail/_refund)`、`m_trade_order(_detail/_pay/_refund)`(场馆+培训共用)、`j_order_ticket(_valid)`、`j_time_card*`、`m_enter_gate`(入闸) | 行为窗口特征、频次/金额/项目分布、时序 |
| 活动互动 | `j_platform_activity_person`、`j_points_records`(积分)、`j_coupon*`、`j_send_prize*` | 活动热衷度、互动偏好特征 |
| 培训/课程 | `t_student_course`、`t_syllabus_student`、`t_class(_teacher)`、`t_student_check`(考勤)、`m_trade_order_course` | 学员×课程关系（→ER 图）、上课频率、进度 |
| 资源/项目 | `m_trade_order_detail(item)`、`sport_id`、`course`、`theatre_ticket*`、`m_group_ticket*`、`p_park_record`(停车) | 「用户×资源」关系表（ER 层产出）、偏好网络、跨品类 |
| 会员/卡/储值 | `h_member_card(_charge/_deducted)`、`j_member_time_card`、`h_card(_vip)` | 消费能力、价值分层（RFM 替代指标） |

**判断结论**：本库**行为数据丰富、关系数据（用户×项目×场馆×课程）充分、但用户无成熟监督标签**。
因此**最可行的是「无监督/自监督」打标（聚类、嵌入、协同），其次是「有监督预测」**（需自主构造监督信号，如历史是否复购/是否流失）。

## 1. 方法一：无监督聚类（★ 首选，最可行）

- **一句话思路**：把"用户行为/属性"压成特征，把用户分成若干语义可解释的簇，每一簇打一个偏好/分层标签。
- **适用性**：本库**核心方法**。不需要任何人工标注，适合无监督、测试期、冷启动。
- **流程（链路）**：
  1. **特征宽表**：一人一行，列=行为窗口指标（近 7/30/90 天订单数、金额、品类分布、频次、最近一次距今天数、积分、活动参与数…）＋静态属性（性别/年龄/城市/会员等级）。
  2. **清洗变换**：缺失值（如金额为 0/负）、去极值、`log1p` 压缩长尾、数值标准化/归一化、类别 one-hot/目标编码。
  3. **降维（可选）**：PCA 去噪、UMAP/t-SNE 可视化，帮助定 K 与解释。
  4. **聚类**：K-means（大样本快）/ GMM（软分配）/ HDBSCAN（自动定簇数、含离群＝沉睡用户）等。
  5. **选 K**：轮廓系数、肘部法则、业务可解释性。
  6. **簇画像**：统计每簇各特征均值→给簇起名（如"高频游泳型 / 周末订场型 / 活动热衷型 / 沉睡流失型"）。
  7. **打标**：输出 `user_id → 簇标签`，写入标签表。
- **资源**：仅 CPU。训练分钟级~小时级；离线每日/每周批量即可。
- **注意**：K 的选择带主观性；需要簇画像保证可解释；纯行为分群不依赖 ER 层（**[A] DWS 直算**）。

## 2. 方法二：图嵌入 / 表征学习（★ ER 关系类首选）

### 2.1 图嵌入是什么（通俗版，写给没学过的人）

**先来个生活化类比：** 想象一张"朋友圈"关系图——每个朋友是一个**点（节点）**，两个人认识就用一条**线（边）**连起来。图嵌入要做的事：**给图上的每个点算一个"坐标"（一串数字，叫向量）**，让"关系近 / 经常一起出现"的点，在坐标空间里也靠得近。

**举个例子（放到本库）：** 游泳馆、健身房、羽毛球馆是三个"点"。如果一个用户既去游泳馆又常去健身房，那么"游泳馆"和"健身房"这两个点在向量空间里就会**挨得很近**；"羽毛球馆"离它们稍远些。于是，当一个用户常去游泳馆时，机器就能顺理成章推断"他大概也喜欢健身房"——因为这两个点在向量空间里离得近。

**为什么要这么做：** 现实业务里"谁和谁有关系"是张巨大的图，人脑和普通表格都很难直接计算。图嵌入把它**压成一个个数字向量**后，机器就能做"找相似人群、自动分群、做推荐"这些事了。这个"把图变成向量"的过程，就叫做**表征学习（Representation Learning）**，学出来的向量叫**嵌入（Embedding）**。

### 2.2 技术流程（以 node2vec 为例）

1. **构造关系表**（ER 层同事产出的「用户×资源」交集/评分）：用户-场馆、用户-运动项目(`sport_id`)、用户-课程、用户-演出。
2. **构图**：把"用户"和"资源(场馆/项目/课程)"都当作**节点**，用户消费过某个资源就画一条**边**；边的粗细＝次数/金额（权重）。
3. **随机游走采样**：想象在图上随机"溜达"——从某个点出发，按一定规则一步步走到邻居，边走边记，形成一串"访问序列"（如 `用户A → 游泳馆 → 用户B → 健身房`）。这一步把图结构翻译成了"一串串路径"，是核心。`node2vec` 的 `p/q` 两个参数控制游走是更"偏本地"(BFS 式)还是更"偏跳远"(DFS 式)。
4. **学向量**：用 NLP 里学"词向量"的 **Word2Vec/Skip-gram** 来"读"这批序列——它发现"游泳馆""健身房"总出现在相似上下文里，于是给它们学出彼此相近的向量。
5. **下游应用**：拿到每个节点的向量后——
   - 对**用户向量**做 K-means → 得到"兴趣类群"（对应匹配表场景 3「兴趣类群」标签）；
   - 算**用户向量之间的余弦相似度** → 找"相似用户 / 相似可推荐资源"。
6. **评估**：把嵌入向量降到 2D 可视化，人工抽查"同类用户/资源是否真的凑在一起"。

> 一句话记忆：**图嵌入 = "随机游走把图变成句子" + "Word2Vec 把句子变成向量"**。

- **适用性**：用于**关系类标签**（相似人群、兴趣类群、偏好向量）；本库关系数据充足，非常契合。
- **资源**：节点数在万~百万级时 CPU 即可；大规模（千万边+）时建议单卡 GPU 加速训练。离线批量。
- **注意**：强依赖 ER 层关系表口径；本质是无监督，无需标注（**[B] ER 关系**；原场景 B 规划，现为扩展项）。

## 3. 方法三：监督/预测（LR / GBDT / XGBoost）（★ 有监督首选，备选）

- **一句话思路**：用历史行为预测未来事件概率，输出"概率型标签"。
- **适用性**：**需先自主构造监督信号**（本库无现成标注）。最可靠的是用历史做代理目标，如：
  - 复购预测：用「T 日前行为」预测「T 日后是否再下单/再入场」；
  - 流失预警：用「过去 30 天特征」预测「未来 60 天是否无任何活动」；
  - 高潜识别：预测未来消费金额/次数分层。
- **流程（链路，关键在防泄漏/切窗口）**：
  1. **构造样本表**：对每个用户切"观察期×标签期"，观察期算特征，标签期算目标 y（0/1 或分档）。
  2. **特征**：同方法一的窗口指标（只用观察期内信息，不用未来——防数据泄漏）。
  3. **训练/验证**：跨期滚动 cohort 按时序切训练/测试（不能随机切，避免时间穿越）；同单期 cohort（全部用户同一观察基准日）可随机分层切，防泄漏由"观察窗/标签窗"构造保证——场景 B 实现即采用此法；类别不平衡用 PR-AUC、下采样/权重。
  4. **输出**：`user_id → 概率`，转分档标签（高危/中危/低危）。
  5. **评估**：AUC/PR、KS、校准曲线；上线后跟踪命中率。
- **资源**：仅 CPU（GBDT/XGBoost 单机绰绰有余）。对比聚类，同类特征下训练稍久但仍分钟级。
- **注意**：**这是唯一"需要目标/标注"的一类**；质量取决于构造目标是否有业务意义。仍属于 DWS 直算（**[A] DWS 直算；本项目已落地为场景 B 流失预测**）。

## 4. 方法四：协同过滤 / 物品向量（Item-based CF / item2vec）

### 4.1 简单介绍（写给没学过的人）

**协同过滤（Collaborative Filtering）的核心直觉一句话：「和你像的人喜欢的，你也可能喜欢」→ 反向推到物品上：「和这个项目很像的项目，你也可能下单」。**

**通俗解释：** 设想有一张巨大的表，行是用户，列是各种运动项目，格子＝用户是否消费过该项目。这张表往往很"稀疏"（大多数人只碰过极少数项目）。协同过滤利用**"某某东西常和某某东西一起被同一个人看上"**这条规律来填空白：
- 发现"游泳　和　健身"经常被同一些用户一起消费 → 得出"游泳 ≈ 健身"；
- 于是给只买过游泳的用户，推健身——哪怕他从没搜过健身。

**和"图嵌入(方法二)"的区别：** 方法二靠"随机游走走遍整张图"来学习结构；方法四更简单，**只盯着"用户×项目"这张共现矩阵做数学计算**（算物品之间的相似度，或直接对矩阵分解）——不用建图、实现更轻量，但少了利用"跨类型关系"的能力。

**item2vec 变体：** 把"一个用户买过的一串项目"当成自然语言里的一个"句子"，用 **Word2Vec** 给每个项目学向量——跟方法二第 4 步同一招，只是不经过"图/随机游走"，直接用行为序列。学完"用户向量＝他买过的项目向量求平均"，即可算相似人群/相似项目。

### 4.2 流程

1. **构造用户-项目矩阵**：行=用户，列=项目(`item`/`sport`/`course`)，值=消费次数/金额（0 或频次）。
2. **方案 A（item2vec）**：把每个用户的一串交互项目当"句子"，Word2Vec 学项目向量 → 用户向量=其项目向量均值。
3. **方案 B（Item-based CF）**：直接算项目间相似度（余弦/Jaccard），给用户"只买过 A"的→推荐与 A 最像的 B/C。
4. **打标/应用**：用户向量做 K-means→"偏好人群"；或算"相似用户"（向量近邻）。
4. **产出**：偏好项目、相似项目推荐、相似人群（向量近邻）。
- **资源**：CPU，内存为主（矩阵规模）。离线批量。
- **注意**：稀疏时效果差；比 node2vec 少利用了"结构关系"，但实现更简单，适合无 ER 层时快速起步。

## 5. 方法五：组合套路（RFM+聚类、嵌入+聚类、多标签）【可扩展】

- **RFM + 聚类**：先构造 最近消费(R)/频率(F)/金额(M) 三维，再聚类或分箱→价值分层。本库可用 储值充值/金额/入闸频次 等替代指标，跨源也可做。
- **嵌入 + 聚类**：方法二产出向量后再聚类=方法二的标准下游。
- **多标签分类**：一人打多枚标签（如既"高频游泳"又"活动热衷"），可用一对其余多模型或阈值法；进阶可用多标签学习（chain / transformer）。本库现阶段**非必需**，作扩展项。
- **序列嵌入**：把用户行为按时间排序成"项目序列"，用 item2vec/序列模型学"下一偏好"——进阶项。

## 6. 方法六：深度序列模型（LSTM / GRU / Transformer）【进阶，本期不优先】

- **一句话思路**：把用户行为当作时间序列，端到端学"行为模式/预测下一行为"。
- **适用性**：本库有行为时间线（订单/入场/消课/停车），理论上可做序列画像或下一行为预测；但**数据质量差、样本大小、部署成本**使其本期性价比低。
- **流程**：行为序列化（按时间排序的离散事件）→ embedding → RNN/Transformer → 分类/自监督。
- **资源**：**通常是唯一明确需要 GPU 的方法**（序列长、参数量大）；训练小时~天级。维护成本高。
- **注意**：列为远期/探索项，不建议作为首阶段部署。

## 优先级小结（供汇报/资源申请）

| 优先级 | 方法 | 标签类型 | 是否需标注 | 是否需 ER | 硬件 |
|---|---|---|---|---|---|
| P0 | 无监督聚类 | 行为/属性类 | 否 | 否（场景A） | 仅 CPU |
| P0 | 监督预测(XGBoost) | 概率/预测类 | 自造标签窗 y | **否（场景B，DWS直算）** | 仅 CPU |
| P1 | 图嵌入 node2vec | 关系/相似类 | 否 | 是（ER） | CPU（大规模+GPU） |
| P1 | Item-based CF / item2vec | 偏好/相似 | 否 | 可不用 | 仅 CPU |
| P2 | 组合套路(多标签等) | 综合 | 视情况 | 视情况 | 仅 CPU |
| P3 | 深度序列 | 序列/预测 | 自监督 | 否 | 需 GPU |

> **核心结论**：本库最可行的是**无监督聚类 + 有监督预测(XGBoost)**两条主线（对应场景 A=DWS 直算聚类、
> 场景 B=DWS 直算流失预测，均不需 ER），自造标签窗 y 可规避无标注问题，CPU 可跑、可解释性强，
> 最适合"从 0 起步 + 测试数据差"阶段。图嵌入(node2vec)保留为扩展项，待 ER 关系数据到位再评估。
