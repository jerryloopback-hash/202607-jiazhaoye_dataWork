# 智能打标调研 · 项目总结报告

> **佳兆业文体用户数据库 · 机器学习打标技术调研与 demo 验证**  
> 面向汇报与后续生产化落地的核心文档。整合方法调研、场景匹配、资源需求、CDP 对接清单、demo 成果。

---

## 一、项目目标与背景

### 1.1 调研目标
在排除基础客观标签、规则标签、统计标签等传统方法的前提下，**调研机器学习/深度学习在用户打标场景中的工程化落地可行性**，并选取典型场景跑通完整打标链路 demo。

### 1.2 数据背景
- **数据源**：佳兆业文体 ODS 层，三套源系统（一起吗 C 端 / 场馆 B 端 / 培训），约 90 张表
- **数据资产**：用户主实体（j_member/h_member/t_student）、消费/交易行为、活动互动、培训课程、资源/项目、会员卡/储值
- **关键特征**：行为数据丰富、关系数据（用户×项目×场馆×课程）充分，但**无成熟监督标签**
- **数仓分层**：ODS → DIM/DWD → DWS → ER → 标签；ER 层由另一位同事负责，我方负责标签层（**场景 A/B 均从 DWS 直算，不依赖 ER**）

### 1.3 测试环境数据质量
- ⚠️ **测试库质量极差**：性别 8956/9008 为"不明"；年龄 9007/9008 无效；订单仅 154 个去重用户且多数对不上会员主表
- **建模前提**：方案设计基于"表名+字段+注释"及生产质量假设；测试库仅用于链路演示，不追求标签质量

## 二、方法调研结论

> 详见 [02_方法调研/方法流程与可行性.md](../02_方法调研/方法流程与可行性.md)

### 2.1 核心结论
本库**最可行的是「无监督聚类 + 有监督预测(XGBoost)」两条主线**（对应场景 A=DWS 直算聚类、场景 B=DWS 直算预测两个分工），二者均无需额外标注（场景 B 自造标签窗 y）、CPU 可跑、可解释性强，是最适合"从 0 起步 + 测试数据差"阶段的组合。

### 2.2 方法可行性排序

| 优先级 | 方法 | 标签类型 | 是否需标注 | 是否需 ER | 硬件 | 流程概要 |
|---|---|---|---|---|---|---|
| **P0** | 无监督聚类 | 行为/属性类 | 否 | 否（场景A） | 仅 CPU | 用户宽表 → log1p/标准化 → PCA → K-means/GMM/HDBSCAN → 簇画像命名 |
| **P0** | 监督预测(XGBoost) | 概率/预测类 | 自造标签窗 y | **否（场景B，DWS直算）** | 仅 CPU | ODS改造→观察窗特征+标签窗y→XGBoost→流失概率 |
| P1 | 图嵌入 node2vec | 关系/相似类 | 否 | 是（ER） | CPU（大规模+GPU） | ER 关系表 → 构图 → 随机游走 → Word2Vec → 用户向量 → 聚类/近邻（扩展） |
| P1 | Item-based CF / item2vec | 偏好/相似 | 否 | 可不用 | 仅 CPU | 用户×项目矩阵 → Word2Vec/余弦 → 偏好向量/相似推荐 |
| P2 | 组合套路(RFM+聚类等) | 综合 | 视情况 | 视情况 | 仅 CPU | RFM 评分 + 聚类 → 价值分层 |
| P3 | 深度序列 LSTM/Transformer | 序列/预测 | 自监督 | 否 | 需 GPU | 行为序列 → embedding → RNN/Transformer → 下一行为预测（远期） |

### 2.3 方法入门讲解（为非算法背景人员补充）
- **图嵌入**：把"用户×资源"关系图压成向量，向量相近=偏好相近；类比"朋友圈关系图给每人算坐标"；核心是"随机游走→Word2Vec"
- **协同过滤**："和你像的人喜欢的，你也可能喜欢"；从用户×项目共现矩阵学相似度

## 三、场景与标签匹配

> 详见 [03_场景与标签需求/场景标签与方法匹配.md](../03_场景与标签需求/场景标签与方法匹配.md)

### 3.1 场景速查表

| 场景 | 标签 | 方法 | 类型 | 需 ER | 优先级 |
|---|---|---|---|---|---|
| **1 C 端消费行为分群** | 行为偏好簇 | 无监督聚类 | A 直算 | 否 | ★ P0（场景A，✅） |
| **2 流失/复购预测** | 概率型标签 | 监督预测(XGBoost) | A 直算 | 否 | ★ P0（场景B，✅） |
| 3 培训课程兴趣/相似学员 | 兴趣类群/相似人群 | 图嵌入 node2vec | B 关系 | **是** | P1（原场景B规划，弃用为扩展） |
| 4 场馆跨品类偏好 | 偏好向量/相似人群 | 图嵌入/CF | B 关系 | 是 | P1 |
| 5 高价值会员分层 | 价值分层 | RFM+聚类 | A 直算 | 跨源需 oneID | P1 |
| 6 序列画像/预测 | 序列偏好 | LSTM/Transformer | A 直算 | 否 | P3 远期 |

### 3.2 首批落地建议
- **场景 A（DWS 直算）**：场景 1 消费行为分群（聚类）——单源、无标注 ✅
- **场景 B（DWS 直算）**：场景 2 流失预警（XGBoost 预测）——自造标签窗 y、不依赖 ER ✅
  （原规划场景 3 图嵌入/ER 已弃用为扩展项）

## 四、硬件资源需求与 CDP 对接

> 详见 [02_方法调研/硬件资源与CDP调研.md](../02_方法调研/硬件资源与CDP调研.md)

### 4.1 资源需求（供服务器采购）

**核心结论**：首阶段按 **CPU 8~16 核 + 32~64GB + 特征/标签存储若干 TB** 部署即可，**不建议预售 GPU**；GPU 仅在二期深度模型时再采购。

| 角色 | 建议规格（起步） |
|---|---|
| 计算/打标节点 | 8~16 vCPU、32~64GB 内存（跑聚类+GBDT+小图嵌入） |
| 特征与标签存储 | StarRocks/ClickHouse + 若干 TB（支持人群圈选位图） |
| 调度/编排 | 复用现有数仓调度器 |
| GPU（可选扩展） | 1×L4/T4（16~24GB），仅在启动深度序列/大规模嵌入时再购置 |

**调度形态**：离线批量（每日/每周触发），不是高并发在线接口 → 成本可控。

### 4.2 CDP 平台需调研/对接清单

智能打标与 CDP 的衔接重点在以下六件事：

1. **标签元数据/血缘**：标签分层（事实/统计/模型/预测）、版本、生命周期、口径注释、血缘可回溯
2. **oneID 实体归一**：三套用户体系（j_member/h_member/t_student）跨源打标需先实体归一，明确由谁做
3. **位图人群圈选**：多标签交集/并集秒级圈选（StarRocks/ClickHouse 位图，或 Druid）
4. **离线调度监控**：调度编排、失败重试、数据监控（标签分布漂移告警）
5. **效果闭环**：标签上线后回测命中率/转化率，定义业务 KPI（召回响应率、续费率、流失挽回率）
6. **隐私合规**：手机号/身份证脱敏、敏感属性、未成年人、标签用于营销的合规边界

**给 IT/供应商的 7 条对接问题**（可直接用）：
1. CDP 是否支持自定义"模型/算法标签"及批量回写？
2. 标签支持位图圈选吗？整数/分布字段如何暴露？
3. 三套用户系统的 oneID 由谁负责、口径是什么？
4. 离线调度器能否挂我们的特征/打标脚本？有没有血缘与监控？
5. 标签能否回溯重算（历史回填）？频率上限多少？
6. 敏感字段脱敏方案与合规审批流程？
7. 上线标签的效果回测/A/B 工具是否具备？

## 五、场景 A demo 成果

> 详见 [04_方案设计与实施/场景A_方案设计与打标模拟.md](../04_方案设计与实施/场景A_方案设计与打标模拟.md)

### 5.1 场景选择
**场景 1：C 端会员消费行为分群**
- **业务目标**：把 C 端会员（一起吗 App）按其消费/活跃行为分成若干可运营人群
- **标签名**：`behavior_cluster`（行为偏好簇）
- **选择理由**：单源（jianengliang 库）、无标注、链路最短，最适合首个完整 demo

### 5.2 数据质量诊断（实测）
- 用户 9008、订单 4668，订单仅覆盖 154 个去重用户且仅 44 个能对上 j_member
- 性别 8956/9008 为 0（不明），年龄 9007/9008 无效
- 可用真实特征：`login_num`（登录次数）、少数用户的订单/活动/积分聚合

### 5.3 方案设计
**特征宽表（8 维）**：age、sex、login_num、order_cnt、total_spend、activity_cnt、points_balance、recency_days
- 真实特征：`login_num` 全真实；订单/活动/积分部分真实
- 缺失/无效字段：用固定种子(seed=2026)随机模型补齐（截断正态/幂律/对数正态/指数），保证可复现

**完整链路**：
1. 连库抽取真实特征 + 模拟补齐缺失字段
2. 清洗变换：log1p 压缩长尾 + StandardScaler 标准化
3. PCA 降维至 2D（解释方差 37.85%）
4. K-means 聚类：遍历 K=2..10，轮廓系数选 K=2
5. 簇画像与命名：统计各簇特征中位数 → 归纳语义标签
6. 输出：标签 CSV（9008 用户×簇名）+ 簇画像表 + PCA 散点图 + 质量报告

### 5.4 demo 结果
- **K=2**，轮廓系数 0.238
- 簇 0（6700 人）：活动互动
- 簇 1（2308 人）：活动互动/沉睡/回流/高活跃
- 产物：
  - `sceneA_behavior_labels.csv`：9008 行，脱敏（仅 user_id + 标签）
  - `sceneA_feature_cluster_profiles.csv`：2 簇画像（各特征中位数）
  - `sceneA_pca_clusters.png`：PCA 2D 散点图（按簇着色）
  - `sceneA_quality_report.txt`：质量报告（标注特征来源 real/simulated）

### 5.5 demo 定位与局限
- ✅ **定位**：跑通完整"特征 → 算法 → 标签"链路，做框架/流程示范，证明方法可落地
- ⚠️ **局限**：测试库数据质量差，缺失特征由模拟主导，**分群结果不代表真实业务人群**；仅证明链路可运行
- 🎯 **生产化建议**：待生产库质量合格后，复用相同脚本框架，用真实特征重跑 → 产出可用标签

## 五点五、场景 B 成果（XGBoost 流失预测 · 生产型全链路，已本机真实跑通）

> 方向调整：场景 B 由「图嵌入/ER 关系」调整为「**XGBoost 预测、DWS 直算**」。
> 详见 [场景B_方案设计与打标模拟](../04_方案设计与实施/场景B_方案设计与打标模拟.md)。

### B.1 场景选择
- **场景 2：C 端会员流失预警**——观察窗历史行为 → 预测未来 30 天是否流失。
- **标签**：`churn_prob`（流失概率）+ `churn_label`（高危/中危/低危-稳定）。
- **类型**：[A] DWS 直算，自造标签窗 y，**不依赖 ER 层** → 可独立落地。

### B.2 工程链路（ODS 改造 → 训练 → 使用 → 增量 → 输出）
1. **ODS 层数据改造**：把 C 端行为源(订单/游泳票/活动/积分/次卡) UNION 成统一事件视图，按 `as_of_date` 滚动窗口，产出
   特征宽表 `dws_user_churn_feature`(观察窗[-180,-1]) + 自造标签表 `dws_user_churn_label`(标签窗[as_of,+30])。
   → SQL：`sceneB/sql/sceneB_ods_to_dws.sql`。
2. **特征工程**：15 维特征(age/sex/login_num/行为量/**近30天事件数**/金额log1p/recency/diversity)；严格观察窗/标签窗切分防泄漏。
   → `sceneB/scripts/sceneB_featurize.py`。
3. **训练/评估**：XGBClassifier + early-stopping + 类别平衡；指标 AUC/PR-AUC/混淆矩阵/特征重要性；模型版本化可回滚。
   → `sceneB/scripts/sceneB_train_xgboost.py`。
4. **工程使用**：标签写回(带 model_version + as_of_date) → CDP 位图圈选高危流失人群 → 召回营销 + 命中率/挽回率回测闭环。
5. **增量优化**：离线批量 + 增量重训（周级全量重训并版本化，保留旧模型；DWS 表按 as_of_date 增量，标签 30 天成熟回填）。
6. **输出**：`sceneB_churn_labels.csv`(user_id+prob+分档+版本+日期) + `sceneB_eval_report.txt` + 版本化模型。

### B.3 数据模拟（脚本 + LLM 增强，均已实测）
- 测试库质量差且本机受限 → 用**合成数据(脚本，latent 驱动) + LLM 增强**模拟生产质量的 ODS 行为流。
- LLM 增强模块插拔式接线本地 LLM（OpenAI 兼容协议），未接线时确定性 mock 回退，管线不中断。
- → `sceneB/scripts/sceneB_synth_data.py` / `sceneB_llm_augment.py` + `sceneB/config/llm_config.json`。

### B.4 demo 结果（2026-09-01 本机真实运行，合成数据口径）
| 项 | 值 |
|---|---|
| 用户数 / 特征 | 12000 / 15 维 |
| 流失率(y=1) | 47.8% |
| 切分 | train 8400 / valid 1800 / test 1800 |
| **AUC / PR-AUC** | **0.7134 / 0.6901**（模型版本 model_20260901_104130） |
| Top 特征 | n_events_30d(0.295) > n_events > recency_days（近30天行为=最强流失信号） |
| 全量打标分布 | 高危流失 24.0% / 中危流失 37.3% / 低危-稳定 38.7% |
| 产物 | features / split / features_augmented / churn_labels / 评估报告 / 版本化模型 均已生成 ✅ |

> ⚠️ 合成数据上的结果证明链路可运行、方法有效（模型学到"近期行为衰减→流失"信号）；真实效果取决于生产数据质量。

### B.5 环境与部署材料
- **环境安装指南** `sceneB/环境安装指南.md`：venv + requirements.txt（numpy2.5.2/pandas3.0.5/sklearn1.9.0/xgboost3.4.1 本机实测）、离线 wheel 安装法、LLM 接入注意事项（unsloth 需先 `/v1/load` 加载模型）。
- **生产部署运行手册** `sceneB/生产部署运行手册.md`：服务器部署五步、调度三件套、监控回滚。

## 六、生产化落地建议

### 6.1 短期（3 个月内）
1. **确认生产库数据质量**：与 DBA/数仓同事确认生产库性别/年龄/订单关联是否合格
2. **场景 A 生产化**：复用 demo 脚本，换生产库连接，跑出真实分群标签 → 小范围 A/B 测试营销转化
3. **场景 B 生产化**：把合成数据替换为生产 DWS 特征/标签宽表，跑真实 XGBoost 流失模型 → 圈选高危流失人群做召回（**完整操作步骤见 [生产部署运行手册](../04_方案设计与实施/sceneB/生产部署运行手册.md)**）
4. **对接 CDP 六件事**：标签元数据、oneID、位图圈选、调度、效果闭环、合规（见 4.2 清单）
5. **场景 B 接入本地 LLM**：✅ 已接入 qwen3.8（`sceneB/config/llm_config.json` enabled=true；接入/加载注意事项见 `sceneB/环境安装指南.md` §2）

### 6.2 中期（6 个月内）
1. **横向扩展场景**：场景 5 高价值会员分层（RFM+聚类）、场景 2 复购/高潜预测变体
2. **场景 B 增量重训练自动化**：Airflow/DolphinScheduler 挂 ODS→特征→训练→打标 链路，版本化 + 监控标签分布漂移
3. **效果闭环**：标签上线后定期回测命中率/转化率，建立"标签→运营→效果→优化"闭环
4. **特征平台化**：沉淀通用特征库（窗口聚合/RFM 替代指标/行为序列），供多场景复用

### 6.3 远期（探索项）
- 深度序列模型（LSTM/Transformer）：需 GPU，训练成本高，待首批标签效果验证后再启动
- 多标签学习：一人多枚标签（既"高频游泳"又"活动热衷"），用多标签分类或阈值法
- 在线实时打标：当前离线批量，若需实时（如入闸后秒级更新标签），需流式计算架构改造

## 八、附录：关键名词解释

- **ODS**：操作数据存储（Operational Data Store），原始数据层
- **DWS**：数据仓库服务层（Data Warehouse Service），汇总宽表
- **ER 层**：Entity-Relationship 层，实体关系层（Inmon 建模）；也指 oneID 实体归一
- **轮廓系数（silhouette）**：聚类质量指标，[-1, 1]，越高越好（簇内紧凑、簇间分离）
- **PCA**：主成分分析（Principal Component Analysis），降维 + 去噪
- **K-means**：经典聚类算法，硬分配，需指定 K
- **node2vec**：图嵌入算法，随机游走 + Word2Vec 学节点向量
- **GBDT/XGBoost**：梯度提升决策树，监督学习，预测类任务首选
- **Item-based CF**：基于物品的协同过滤，从用户×项目共现矩阵学相似度
