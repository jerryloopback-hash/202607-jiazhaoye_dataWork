## 0. 一图看懂：这套东西做什么

```
用户行为数据          特征宽表                模型                标签
(谁在什么时候      (一人一行，15列指标)   (机器学习/规则)   (每人一个流失概率+分档)
 买票/下单/活动)  ──►  features.csv   ──►  训练(4选1方法) ──►  sceneB_churn_labels.csv
                                                                    │
                                                    高危流失人群 ──► CDP圈选 → 召回营销
```

**四种方法，一个参数切换**（详见 §4）：

| 参数值 | 方法 | 一句话定位 |
|---|---|---|
| `xgboost` | XGBoost 梯度提升树 | **生产主力方法**，精度与速度平衡 |
| `lr` | 逻辑回归 | 线性基线，系数可解释，最快 |
| `rf` | 随机森林 | bagging 树，稳健，常与 XGB 互有胜负 |
| `rule` | RFM 规则评分卡 | 传统方法对照（无训练），回答"机器学习比规则好多少" |

> 同一台机器、同一份数据可以随时切换重跑，互不影响；每个模型按"方法+时间戳"独立存档。

## 4. 方法怎么选（路由参数一览）

主程序 `sceneB_model_router.py` 的完整用法：

```bash
.venv/bin/python scripts/sceneB_model_router.py                    # xgboost 训练+打标（默认；只产新版本，不改上线指针）
.venv/bin/python scripts/sceneB_model_router.py --model lr         # 换逻辑回归
.venv/bin/python scripts/sceneB_model_router.py --model rf         # 换随机森林
.venv/bin/python scripts/sceneB_model_router.py --model rule       # 传统 RFM 评分卡
.venv/bin/python scripts/sceneB_model_router.py --compare          # 四方法同台对比
.venv/bin/python scripts/sceneB_model_router.py --mode predict     # 日常打标（不训练）
.venv/bin/python scripts/sceneB_model_router.py --deploy 版本号     # 显式上线指定版本（唯一改 latest.json 的入口）
```

> ⚠️ **上线指针规则（2026-09-02 起）**：训练与对比**只产生新版本文件、不自动改 `latest.json`**；
> 上线/回滚一律用 `--deploy <版本号>` 显式切换。这样任何"试试规则/换方法跑跑看"的训练都
> 不会意外覆盖线上模型（9-01 曾发生 rule 测试训练覆盖 RF 上线指针的事故）。

**同台对比实测**（2026-09-02，服务器同版本环境 `.venv312`，训练数据含 LLM 校准标签 y_aug；生产数据上请用 `--compare` 重跑得出你自己的结论）：

| 方法 | AUC | PR-AUC | 训练耗时 | 特点 |
|---|---|---|---|---|
| 随机森林 | **0.7801** | 0.7439 | 1.9s | 本次最优，稳健 |
| RFM 规则评分卡 | 0.7708 | 0.7176 | 0s | 传统对照（LLM 校准标签后规则也水涨船高） |
| **XGBoost** | 0.7697 | 0.7248 | 1.6s | 主方法，生产更大数据量下通常更强 |
| 逻辑回归 | 0.7638 | 0.7193 | 0.1s | 最快、系数可解释 |

**怎么选**：
- 生产主力用 `xgboost`（数据量大、非线性关系多时优势明显）；
- 上线前跑一次 `--compare`，若 `rf`/`lr` 在你的真实数据上更优，用 `--deploy <该方法的版本号>` 显式上线它；
- 保留 `rule` 的对比结果进汇报——它是"智能标签比传统规则好多少"的直接证据。

**RFM 规则怎么调参（免改代码，2026-09-03 起）**：

`rule` 方法的分箱边界、三维权重、分档阈值全部由调参脚本在命令行传入，运营/调度传参即可，无需读改源码：

```bash
# ① 按传入参数调参（未传的参数用内置默认口径；注意 M 边界是 spend_total 的 log1p 值）
.venv/bin/python scripts/sceneB_rfm_tuner.py \
    --input output/features.csv \
    --r-bins 7,30,90,180 --f-bins 0,3,10,25 --m-bins 0,3,5,7 \
    --weights 0.4,0.35,0.25 --churn-high 0.7 --churn-mid 0.4

# ② 自动调参：分箱按训练集分位数生成 + 权重网格搜索测试集 AUC 最优（显式传入的参数优先）
.venv/bin/python scripts/sceneB_rfm_tuner.py --auto --input output/features.csv

# ③ 按业务名单量定分档（如召回预算只够圈 10% 用户 → 高危占比≈10%、中危≈20%）
.venv/bin/python scripts/sceneB_rfm_tuner.py --target-high-rate 0.10 --target-mid-rate 0.20 --input output/features.csv
```

脚本产出：调参版评分卡 `output/model/model_rule_<时间戳>.json`（分箱/权重/阈值全参数存档）、
打标预览 `sceneB_churn_labels_rule_tuned.csv`、调参报告 `sceneB_rfm_tune_report.txt`
（含与默认规则的 AUC 对比、分档分布合理性提示、建议的上线命令）。
**调参不改上线指针**——报告达标后按报告执行 `--deploy rule_<时间戳>` 上线；回滚 = `--deploy` 旧版本号。
上线后 `--mode predict` 的打分与分档自动使用调参参数（分档阈值随 rule 版本一并写入指针）。

## 5. 接真实数据：输入是什么格式（最重要一节）

主程序只吃**一个文件**：特征宽表 CSV（默认 `output/features.csv`）。一行 = 一个用户。

**字段定义（16 列，列名必须一字不差）**：

| 列名 | 类型 | 含义 | 缺失/约定 |
|---|---|---|---|
| `uid` | 字符串/整数 | 用户唯一 id（内部 id，**不要用手机号**） | 必填 |
| `age` | 整数 | 年龄 | 未知填 0 |
| `sex` | 整数 | 性别 0未知/1男/2女 | 未知填 0 |
| `login_num` | 整数 | 累计登录次数 | 无则 0 |
| `n_events` | 整数 | **观察窗内**（如近180天）行为总次数 | 无则 0 |
| `n_events_30d` | 整数 | 观察窗**最近30天**行为次数（最强流失信号） | 无则 0 |
| `n_order` | 整数 | 订单数 | 0 |
| `n_swim` | 整数 | 游泳票/票据核销数 | 0 |
| `n_activity` | 整数 | 活动参与数 | 0 |
| `n_points` | 整数 | 积分变动次数 | 0 |
| `n_timecard` | 整数 | 次卡使用次数 | 0 |
| `spend_total` | 小数 | 消费总额（已做 log1p） | 0 |
| `spend_mean` | 小数 | 平均客单（log1p） | 0 |
| `spend_max` | 小数 | 单笔最大（log1p） | 0 |
| `recency_days` | 整数 | 最近一次行为距今天数 | **观察窗内无行为填 999** |
| `behavior_diversity` | 小数 | 涉及行为类型数/5（0~1） | 0 |
| `y` | 0/1 | **训练必需**：1=未来30天流失，0=活跃 | 打标时可不要此列 |

> ⚠️ 防泄漏口径：特征只统计"观察窗"（过去 N 天），`y` 来自之后的"标签窗"（未来 30 天），两段窗口**不能重叠**。`log1p` 即 `ln(1+金额)`，与 SQL 里的 `LOG1P()` 一致——如果直接导原始金额不取 log，模型仍能跑但与 demo 口径不一致。

**这份 CSV 从哪来（生产）**：由数仓按 `sql/sceneB_ods_to_dws.sql` 建 `dws_user_churn_feature`（特征）与 `dws_user_churn_label`（y），两表按 `user_id, as_of_date` JOIN 后导出 CSV，列顺序对照上表。SQL 里每列的计算口径已写好（观察窗 180 天聚合 + 标签窗 30 天自造 y）。

**`split.json` 不用自己准备**：训练时若目录下没有 `split.json`，主程序会自动按 70/15/15 随机分层切分并生成（固定 seed，可复现）。

**可选 LLM 校准标签 `y_aug`**：若输入数据来自 LLM 增强流程（`scripts/sceneB_llm_augment.py` 产出的 `features_augmented.csv`），训练时检测到 `y_aug` 列会**自动优先用它作为 y**（LLM 仅对 frac 比例样本做业务语义二次校准，其余保持脚本标签；2026-09-02 实测 600 条校准、与脚本标签一致率 65.2%，AUC 较纯脚本标签 +5.6pt）。

## 6. 训练模型（`--mode train`，默认模式）

```bash
.venv/bin/python scripts/sceneB_model_router.py --model xgboost
```

程序依次做 4 件事：读数据 → 训练（自动处理类别不平衡、early-stopping）→ 在测试集出评估报告 → **保存模型 + 对全部用户打一遍标签**。

**训练完检查三件事**：
1. **AUC 达标**：看终端输出或 `output/sceneB_eval_report.txt`。经验线 ≥0.75（模拟数据 0.71 属正常，真实生产数据视质量而定）；
2. **特征重要性说得通**：报告末尾 Top10 里 `n_events_30d`/`recency_days`/`n_events` 应排前面——若乱七八糟的特征居首，先查数据口径；
3. **分档占比合理**：高危档一般 5%~20%。异常（如 50%+）说明阈值或数据有问题，先别上线。

模型文件落在 `output/model/model_xgboost_<时间戳>.json`。**此时新版本尚未上线**（`latest.json` 未变）：
评估达标后执行 `python scripts/sceneB_model_router.py --deploy xgboost_<时间戳>` 才切到新版本。

## 7. 跑标签（`--mode predict`，日常打标就用它）

生产上**每天打标不应该重新训练**。用已上线的模型对新数据打标：

```bash
# 把当天导出的特征宽表放到任意位置，然后：
.venv/bin/python scripts/sceneB_model_router.py --mode predict --input /data/features_20260901.csv

# 不传 --input 时，默认读 output/features.csv
.venv/bin/python scripts/sceneB_model_router.py --mode predict
```

- 程序读 `output/model/latest.json` 找到当前上线模型 → 对输入文件**每一行**输出流失概率与分档 → 写 `output/sceneB_churn_labels.csv`。
- 输入文件**不需要 `y` 列**（y 只在训练时用），有也会被忽略。
- 几万~百万行都在秒~分钟级完成（纯 CPU）。

**输出标签表格式（与生产库 `dws_user_churn_label_result` 一致）**：

| 列名 | 类型 | 含义 |
|---|---|---|
| `user_id` | 同输入 uid | 用户唯一 id |
| `churn_prob` | 小数 0~1 | 未来30天流失概率（保留4位） |
| `churn_label` | 文本 | 分档：`高危流失`(≥0.7) / `中危流失`(≥0.4) / `低危/稳定`(<0.4) |
| `model_version` | 文本 | 打标所用模型，如 `xgboost_20260901_144225`（方法+时间戳，可回溯） |
| `as_of_date` | 日期 | 打标基准日 |

示例：

```csv
user_id,churn_prob,churn_label,model_version,as_of_date
U000001,0.8312,高危流失,xgboost_20260901_144225,2026-09-01
U000002,0.4417,中危流失,xgboost_20260901_144225,2026-09-01
U000003,0.1203,低危/稳定,xgboost_20260901_144225,2026-09-01
```

落库：把 CSV Stream Load / INSERT 进 `dws_user_churn_label_result`（建表语句在 `sql/sceneB_ods_to_dws.sql` 表3），下游 CDP 按 `churn_label='高危流失'` 圈人。阈值 0.7/0.4 想调整：ML 方法改脚本顶部 `CHURN_HIGH, CHURN_MID` 两个常量后重跑；rule 方法直接用 `sceneB_rfm_tuner.py` 传参调整（`--churn-high/--churn-mid/--target-high-rate`，见 §4）。

## 8. 增量训练怎么操作（每周/每月一次）

"增量"在本方案里 = **用累积的最新全量样本重训一个新版本**（树模型标准做法），旧模型全保留、随时可回滚：

```bash
# 第 1 步：数仓刷新特征/标签表后，导出最新训练集（含新成熟的样本）
#   （SQL: dws_user_churn_feature JOIN dws_user_churn_label，见生产部署运行手册 §3）

# 第 2 步：重训（会自动生成新版本，不影响线上）
.venv/bin/python scripts/sceneB_model_router.py --model xgboost

# 第 3 步：看新版本评估报告
cat output/sceneB_eval_report.txt
```

**上线/回滚判定**：
- 新版本 AUC **不低于**旧版本（或达到业务达标线）→ 显式上线：`python scripts/sceneB_model_router.py --deploy <新版本号>`，次日打标自动用新模型；
- 新版本**变差** → 什么都不用做，指针保持旧版本即可（训练不改指针）；万一线上已需回退，`--deploy <旧版本号>` 指回旧模型（`output/model/` 下历史全在），然后重跑 `--mode predict` 刷新标签。

这就是"版本化 + 指针"机制：**训练永远只产生新文件、不覆盖旧文件；上线与否只由 `--deploy` 对 `latest.json` 的显式操作决定**。

## 9. 四方法对比怎么跑（汇报/选型用）

```bash
.venv/bin/python scripts/sceneB_model_router.py --compare
```

程序用**同一份切分**把四种方法各训一遍、同一测试集出分，终端打印对比表，并落盘 `output/sceneB_model_comparison.txt`；每个方法的标签分别存为 `sceneB_churn_labels_<方法名>.csv` 便于抽查。**对比只产出版本、不自动改上线指针**——确认最优方法后用 `--deploy <该方法版本号>` 显式上线（报告末尾会印出建议的版本号）。对比结论直接可用于汇报："机器学习（XGB/RF/LR）整体优于传统 RFM 规则"（模拟数据实测 AUC +0.9~1.7 个百分点，生产数据需重跑）。

## 10. 常见问题（FAQ）

**Q1：模型文件在哪？为什么有好几个？**
`output/model/` 下，`model_<方法>_<时间戳>.<json|joblib>`，每个版本独立保留（回滚用）；`latest.json` 是唯一"上线指针"。

**Q2：换了方法（如 --model lr）会覆盖之前的 XGBoost 模型吗？**
不会。方法名在版本号里，各存各的；且训练**不改** `latest.json`——想切到哪个版本就 `--deploy` 哪个。

**Q3：打标时报"找不到特征列"？**
输入 CSV 的列名必须与 §5 表格一字不差（区分大小写、下划线）。先用 `head -1 文件.csv` 核对。

**Q4：`recency_days=999` 是什么？**
约定值：该用户在观察窗内**没有任何行为**（最可疑的流失人群）。导入真实数据时照此约定填。

**Q5：每天打标用哪个命令？会不会越跑越慢？**
`--mode predict`，不训练、只推理，秒~分钟级；与训练完全独立。

**Q6：想用别的方法（如 LightGBM）？**
脚本方法注册表是插件式的：在 `fit_method()`/`save_model()` 里照 `rf` 的样子加一个分支即可，路由/评估/打标逻辑全部复用。

**Q7：LLM 增强是必须的吗？**
不是。它只用于 demo 数据的"业务合理性增强"（`sceneB_llm_augment.py`），生产训练直接吃 DWS 导出的真实数据，与 LLM 无关。LLM 不可用时自动 mock 回退，管线不中断。

**Q8：想调 RFM 规则的分箱/权重/分档阈值，一定要改代码吗？**
不用。用 `scripts/sceneB_rfm_tuner.py` 传参调参（见 §4），产出新的 rule 版本后 `--deploy` 上线。直接改代码里的 `RULE_PARAMS` 常量也有效，但传参方式可被调度重复执行、产出带完整参数的版本档案、可对比 AUC，推荐传参。
